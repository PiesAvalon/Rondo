# `TensorReferenceAnalysis` does not implement the SymPy handlers the interpreter registry declares, so `torch.compile(dynamic=True)` crashes on ordinary Python scalar arithmetic

**Component:** `torch.compile` (Dynamo) → `torch/fx/passes/_tensorify_python_scalars.py`
**Severity:** crash (compilation failure) — valid eager programs cannot be compiled
**Status:** present on `main` (verified against `main` sources for both files)
**Supersedes:** the earlier drafts `RONDO-PT-001` (`python_mod`) and `RONDO-PT-002` (`expr_cond_pair`) — same root cause, two triggers
**Found with:** Rondo differential oracle (Reference/eager vs Fresh-compiled) + symbolic-scalar fuzzing

---

## Summary

When `torch.compile` is used with dynamic shapes, Dynamo converts Python scalar
expressions that depend on symbolic values into SymPy expressions and evaluates them
with a *reference analysis*. `torch/fx/passes/_tensorify_python_scalars.py:157` selects

```python
Analysis = TensorReferenceAnalysis
```

and `torch/utils/_sympy/interp.py` dispatches every SymPy node with

```python
handler = getattr(analysis, handler_name)
```

The handler names come from the registry in `handlers()` in the same file. That registry
declares **eight** handlers that `TensorReferenceAnalysis`
(`torch/utils/_sympy/reference.py`) does not implement:

```
expr_cond_pair, identity, is_non_overlapping_and_dense_indicator,
modular_indexing, piecewise, python_mod, trunc, where
```

Three of them are reachable from public API — `python_mod`, `expr_cond_pair` and
`piecewise` — so ordinary Python expressions such as `float(k % 3)` or
`float(torch.sym_ite(k > 2, 1, 0))` abort compilation with a bare `AttributeError`.

## Minimal reproducers

```python
import torch

# 1) python_mod -- Python int modulo on a dynamic scalar
def f(x, k):
    return x + float(k % 3)

# 2) expr_cond_pair (and then piecewise) -- symbolic ternary
def g(x, k):
    return x + float(torch.sym_ite(k > 2, 1, 0))

x = torch.randn(4, 3)
f(x, 5); g(x, 5)                     # eager: both fine

torch.compile(f, dynamic=True)(x, 5)
# BackendCompilerFailed: backend='inductor' raised:
#   AttributeError: type object 'TensorReferenceAnalysis' has no attribute 'python_mod'

torch.compile(g, dynamic=True)(x, 5)
# BackendCompilerFailed: backend='inductor' raised:
#   AttributeError: type object 'TensorReferenceAnalysis' has no attribute 'expr_cond_pair'
```

`f` needs no tensors at all beyond the one it adds to; the crash is purely a function of
the scalar expression. `float(...)` is not required — using the value as a shape fails the
same way.

## Reproduction results

`python repro.py --replays 3` (in this directory):

| trigger | eager | compiled (`dynamic=True`) |
|---|---|---|
| `float(k % 3)` | ok | **AttributeError: no attribute `python_mod`** |
| `float(fa % 2.5)` (float modulo) | ok | **AttributeError: no attribute `python_mod`** |
| `float(torch.sym_ite(k > 2, 1, 0))` | ok | **AttributeError: no attribute `expr_cond_pair`** |
| nested `sym_ite` | ok | **AttributeError: no attribute `expr_cond_pair`** |
| control: `float(k // 3)` | ok | ok |

* 8/8 non-control runs fail (4 cases × CPU + CUDA), 3/3 replays each, deterministic.
* `dynamic=False` is unaffected (no symbolic scaling), which is why static-shape CI does not catch it.

## Which handlers are actually reached

`handler_probe.py` in this directory installs a probing metaclass over
`TensorReferenceAnalysis` whose `__getattr__` records every missing handler the
interpreter requests while a program is compiled. It produces:

| program | missing handlers requested |
|---|---|
| `x + float(k % 3)` | `python_mod` |
| `x + float(fa % 2.5)` | `python_mod` |
| `x + float(torch.sym_ite(k > 2, 1, 0))` | `expr_cond_pair`, **`piecewise`** |
| nested `sym_ite` | `expr_cond_pair`, **`piecewise`** |
| `x + float(k // 3)` (control) | — |

So the sym_ite path is broken **twice**: `sym_ite` is lowered to a `sympy.Piecewise`
whose `ExprCondPair` is evaluated first, and the enclosing `Piecewise` is evaluated next.
Adding only the `expr_cond_pair` handler converts the failure into a `piecewise` failure.
Any fix should implement the whole reachable set.

## Root cause

`torch/utils/_sympy/interp.py::handlers()` maps:

```python
PythonMod: "python_mod",
sympy.functions.elementary.piecewise.ExprCondPair: "expr_cond_pair",
sympy.Piecewise: "piecewise",
...
```

but `torch/utils/_sympy/reference.py::TensorReferenceAnalysis` defines no
`python_mod`, `expr_cond_pair` or `piecewise` method. `sympy_interp` therefore raises
`AttributeError` on `getattr(Analysis, handler_name)`.

The other five absent handlers (`identity`, `is_non_overlapping_and_dense_indicator`,
`modular_indexing`, `trunc`, `where`) are generated by Inductor's index-expression
machinery rather than by Dynamo's scalar tensorification, so they are latent rather than
immediately user-reachable — but they are the same defect and are one code path away.

## Suggested fix

Implement the missing handlers on `TensorReferenceAnalysis`, or fail loudly with a
supported-handler check. Concretely:

* `python_mod` — Python `%` semantics (result has the sign of the divisor), which differ
  from `mod`/`Mod`; it cannot simply alias `self.mod`.
* `expr_cond_pair(pred, then, other)` — the per-branch pair used by `piecewise`.
* `piecewise(*pairs)` — select the value of the matching branch.
* `trunc`, `where`, `identity`, `modular_indexing`,
  `is_non_overlapping_and_dense_indicator` — mirror the implementations that already
  exist in the other analyses (`OptimizedPythonReferenceAnalysis`,
  `SymPyValueRangeAnalysis`), or add an explicit `NotImplementedError` with the handler
  name so the failure is actionable.

A cheap structural guard is to assert at import time that every name in
`interp.handlers().values()` exists on the analysis class, which turns a user-facing
crash into a startup error.

## Prior art

* Searches on the PyTorch tracker for `python_mod`, `expr_cond_pair` and
  `TensorReferenceAnalysis has no attribute` return no matching report.
* #133655 touches the same file but is about a different mechanism (restart analysis),
  not missing handlers.
* The `handlers()` registry and the `TensorReferenceAnalysis` class are both unchanged on
  `main`.

## Impact

Any `torch.compile(dynamic=True)` program that performs Python-level modulo or a
symbolic ternary on a dynamic scalar crashes. Both are natural patterns:
`float(k % 3)`, `int(n % 2)`, index math over dynamic sizes, and
`torch.sym_ite(cond, sym, 1)` bound clamping. The failure mode is a compiler
`AttributeError`, which gives the user no hint about which construct is unsupported.
